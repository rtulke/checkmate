# CIS benchmarks

Automated checks for CIS benchmarks. The Linux policies are generated by
`tools/cis-import` from the goss audit content of
[Ansible Lockdown](https://github.com/ansible-lockdown) (MIT license), the macOS
policies by `tools/mscp-import` from the
[macOS Security Compliance Project](https://github.com/usnistgov/macos_security)
(CC BY 4.0); see [NOTICE](NOTICE). Do not edit the policies by hand; change the
converters and run `make cis-import`.

| Policy | Benchmark |
|---|---|
| `rhel7.yml` – `rhel10.yml` | Red Hat Enterprise Linux 7–10 and rebuilds (Rocky, Alma, Oracle, CentOS) |
| `debian11.yml` – `debian13.yml` | Debian 11–13 |
| `ubuntu18.yml` – `ubuntu26.yml` | Ubuntu 18.04, 20.04, 22.04, 24.04, 26.04 LTS |
| `suse15.yml`, `suse16.yml` | SUSE Linux Enterprise / openSUSE Leap 15 and 16 |
| `amazon2.yml`, `amazon2023.yml`, `amazon2027.yml` | Amazon Linux 2, 2023 and 2027 |
| `win11.yml`, `win2019.yml`, `win2022.yml`, `win2025.yml` | Windows 11 Enterprise, Windows Server 2019, 2022, 2025 (run elevated) |
| `macos14.yml`, `macos15.yml`, `macos26.yml` | Apple macOS 14 Sonoma, 15 Sequoia, 26 Tahoe (run with `sudo`) |
| `postgresql.yml` | PostgreSQL 12 and later, written by hand (run with `sudo`) |
| `apache.yml` | Apache HTTP Server 2.4 on RHEL-like systems and Debian/Ubuntu, written by hand (run with `sudo`) |

Each policy only runs on its own platform (`defaults.when`).

## Selecting profiles

| Tag | Selects |
|---|---|
| `cis` | every CIS check |
| `cis-rhel9`, `cis-debian12`, … | one benchmark |
| `cis-level-1` | Level 1 recommendations |
| `cis-level-2` | Level 2 profile (includes Level 1) |
| `cis-server`, `cis-workstation` | recommendations of the server or workstation profile |
| `cis-level1-server`, `cis-level2-server`, `cis-level1-workstation`, `cis-level2-workstation` | the four CIS profiles |
| `cis-section-1` … `cis-section-7` | one chapter of the benchmark |
| `nist-800-53r5-low/-moderate/-high`, `nist-800-171`, `disa-stig`, `cmmc-level-1/-2` | macOS checks that are also part of these baselines |

macOS has no server/workstation split; use `cis-level-1` or `cis-level-2`.
PostgreSQL has the profiles `cis-postgresql-db` and `cis-postgresql-linux`.

`postgresql.yml` is not generated. It reads the settings of the running
server with psql (`SHOW`, `pg_settings`, `pg_hba_file_rules`), so values from
`postgresql.conf`, `postgresql.auto.conf` and `ALTER SYSTEM` all count. If
psql cannot connect as postgres over the local socket, the first check is an
ERROR and the others are skipped.

`apache.yml` is not generated either. It takes the list of configuration files
from `httpd -t -D DUMP_INCLUDES` (`apache2ctl` on Debian and SUSE; on RHEL 8 and
later `apachectl` no longer passes options to httpd), so only files httpd really
reads count. If the configuration is invalid, the first check fails and the
others are skipped. A missing `SSLProtocol` is accepted on systems with a
crypto policy other than LEGACY, which already limits OpenSSL to TLS 1.2.

```bash
checkmate run cis/rhel9.yml --tags cis-level1-server
checkmate run cis/debian12.yml --tags cis-level-2+cis-server --skip-tags cis-section-1
checkmate run cis/ubuntu24.yml --id 'CIS-UBUNTU24-5.1.*' -v
```

Check IDs contain the recommendation number (`CIS-RHEL9-5.1.20-…`), so `--id`
selects single recommendations or whole sections.

## How the conversion works

| goss resource | checkmate check |
|---|---|
| `command` | the same command; exit code and stdout patterns become `rc` and `some`/`none` expectations |
| `file` | existence, type, link target, owner and group, and mode "as strict or stricter" via `find -perm`; content patterns via `some`/`none` |
| `package` | `rpm -q` or `dpkg-query` |
| `service` | `systemctl show` (resolves aliases, works on RHEL 7) |
| `mount` | `findmnt` with the required options |
| `kernel-param` | `sysctl -n` |

For macOS, mSCP rules tagged `cis_lvl1`/`cis_lvl2` are taken over with their
check script and expected result; organization-defined values use the CIS
value. Many of them read managed preferences, so on a Mac without a
configuration profile (MDM) they fail even if the setting was made by hand,
exactly as in mSCP. Rules without an automated check are left out. Every
check carries the mSCP discussion as rationale and the mSCP fix as
remediation; for rules implemented by a configuration profile the
remediation lists the payload settings (and the declarative device
management setting, where mSCP names one).

For Windows, the upstream audits read most values from one shared snapshot
(one secedit export, one auditpol call, ...) written before the checks run.
checkmate checks stay independent: every generated check collects its own
value (registry value, secedit setting, user right, audit subcategory,
service start type, firewall profile, per-user policy) with the same logic as
the upstream collector. The server audits render differently per system role,
so they are rendered for every role and merged; role-specific checks depend on
`cis_windows_role` (`member` by default, `standalone` or `dc`). Windows 11
uses `cis_windows_domain_joined` for the password and lockout rules a domain
policy sets. The Server 2016 audit is not converted: it depends on
pre-generated gpresult and audit files.

Deviations from the Ansible Lockdown content, each applied deliberately:

- A disabled kernel module may point to `/bin/true` or `/bin/false`.
- Content checks of `/etc/ssh/sshd_config` include `/etc/ssh/sshd_config.d/*.conf`.
- `MaxSessions 10` is accepted (an upstream pattern also matched 10).
- APT accepts `"false"` as well as `"0"` for `Install-Recommends`/`Install-Suggests`.
- "No password change date in the future" uses one robust command on every
  platform; the upstream variants compared dates as strings or passed when
  `chage` printed `never`.
- The SSH banner file check reports "no banner configured" instead of failing
  in `stat` when no banner is set.
- Commands that are not valid shell code upstream are left out and listed by the converter.

## Accepted deviations

Do not edit the generated policies to silence a finding. Keep accepted
deviations in a waiver file with a reason and an expiry date and pass it with
`--waivers` (see the [waivers reference](https://rtulke.github.io/checkmate/reference/waivers/)):

```yaml
waivers:
  - id: CIS-RHEL9-1.1.2.1.*
    reason: /tmp is a tmpfs mount managed by systemd
    until: 2027-06-30
```
